# PRD panel and layout

- Add only the frontend code needed for the PRD panel. Pressing the left and right Alt keys together toggles it on the right of the prototype. With no component selected, show the current page's full PRD. While the mode is open, clicking a functional section or standalone component selects only its PRD and does not trigger that component's normal action; show one icon-only left-arrow button in every component PRD header, immediately before the close button, with tooltip and accessible name "返回整页 PRD". The arrow clears the component selection and highlight and opens the independent full-page PRD for the current page, step, or review stage; it does not close the panel or change the prototype view. Hide the arrow in full-page mode and keep it available in both local editing and deployed read-only modes. Returning must preserve pending component edits in their original file and must not merge or copy component content into the full-page PRD. When the mode is closed, preserve the prototype's existing appearance and interactions. If the browser or system does not deliver this shortcut reliably, ask before choosing a different one.
- When editing an in-scope PRD panel after the first extraction, keep its header compact without unused placeholder space and keep the mapped PRD file path visibly displayed, not only in a hover tooltip. If the panel title repeats a component PRD's opening heading, hide only that duplicate heading in the rendered component body. Do not remove it from the Markdown source or change the full-page PRD display or content; follow the project's existing visual language.
- For each page or component PRD already in the enabled PRD scope, show two switchable tabs labeled `交互效果及数据流` and `验收要点` when that PRD is next explicitly touched. Place existing content in the appropriate tab only when its heading or meaning makes the classification clear; ask the user before classifying ambiguous content. Preserve manually edited text and the order within each category, invent no missing requirements, and save edits from both tabs to the same mapped Markdown file without losing content. Do not scan, migrate, or rewrite untouched PRDs or add unrelated pages to the PRD scope to satisfy this rule.
- While PRD mode is open, keep all prototype UI, including its top navigation, system drawers such as the message center, dialogs, popovers, and backdrops, inside the left prototype region; reserve a separate region at the far right for PRD with no horizontal or vertical overlap. Constrain fixed or teleported prototype overlays, styles, stacking, event capture, focus handling, and scroll locks to the prototype region so they cannot cover, dim, restyle, intercept input from, or disable editing and scrolling in PRD. Selecting a prototype component changes only the corresponding PRD selection and content; preserve independent layout, scrolling, and close actions. If available width cannot keep both regions usable, ask the user to choose the narrow-screen arrangement before implementing it. Check the affected simultaneous-open state once, including any relevant top bar or overlay; during a first `extract`, defer this new layout behavior to the subsequent `extend` step so the source styles remain unchanged.
- Use the project's explicit development and deployment modes to make local runs editable and the uploaded or deployed version read-only; do not infer this distinction from the URL alone. Keep page and component PRD viewing available in the deployed version, but do not expose editing controls, editable content, drag handles, auto-save, or local file-write requests there. Publishing does not disable editing in a separately running local checkout.
