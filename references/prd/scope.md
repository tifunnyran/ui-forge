# PRD scope and mappings

- When enabled, use the actual current or user-specified prototype page and any existing requirements to write or update its corresponding PRD. Cover only that page and its functional sections and standalone components; add other pages only when requested. Store page and selectable-component PRDs as ordinary `.md` files in a dedicated `src/prd/` directory relative to the frontend project root; create the directory when needed. Move existing in-scope PRD files there without losing content, and ask before resolving ambiguous mappings or duplicate files. Read any existing PRD first and retain content that is consistent with the prototype. Distinguish observed UI from confirmed intended behavior; ask about material gaps or conflicts rather than inventing requirements.
- Map each in-scope page and each selectable component whose PRD has not been explicitly disabled by the user to its own stable `.md` path in `src/prd/` by default. Reusing a frontend component does not itself authorize sharing its PRD file. Before creating a PRD path for a module that may be shared, verify its actual uses and ask the user whether the named selections should share one PRD. If approved, create one common file and map those confirmed uses to it from the start; otherwise keep separate paths. Record each approved shared-file exception in the project's mapping. Before changing mappings, inspect the affected paths in both directions; if an unapproved path is shared, name every affected selection and ask the user how to separate it before editing.
- When separating an existing shared PRD, preserve its text and manual edits, change only the in-scope mappings, and do not overwrite another selection's content. If a mapped file does not exist, check for recorded user-approved deletion or disablement first; create an empty file only if its PRD remains enabled. An empty file means the PRD has no content yet, not that the user must choose a file. Open enabled mapped files directly in the panel, editable when running locally and read-only in the deployed version, without inventing placeholder requirements or creating PRDs for unrelated pages. After a mapping change, make one focused check that each affected selection opens the intended path and edits remain isolated except for explicitly approved sharing.
- In local editing mode, provide a delete control in every component PRD header. Before deletion, show a confirmation dialog identifying the selected component and its mapped file; affirmative confirmation authorizes deleting that file and durably disabling that component's PRD. Preserve the prototype component and the independent full-page PRD. If the file is shared, confirm the named affected uses before deleting it. Cancellation or failure must keep the content available; report success only after the file deletion and disablement are saved. Later selections, refreshes, preview restarts, and AI PRD synchronization must honor the disabled mapping and must not recreate the file unless the user explicitly requests restoration. Deployed read-only builds must honor disabled mappings and expose no delete control or deletion operation.
